# AquaPilot 质量路线图

> 目标不是"再加几个功能"，而是把这个原型从**看起来专业**推到**专业可信**。
> 每条都给出：为什么现在的实现不够、改成什么、怎么证明改对了、代价多大。
> 依据：(1) 当前代码的真实审查结论；(2) 实测性能（`scripts/bench.ts`）；(3) 已核实的国际基准 BSM1/ASM1 权威参数。

---

## 0. 先看事实

### 0.1 实测性能（`npx tsx scripts/bench.ts`）

| 指标 | 实测值 | 意味着什么 |
|---|---|---|
| 单步仿真（1 min 步长） | 0.0032 ms | 单核可同时驱动 215 座厂；性能不是瓶颈 |
| 单次 4 h 预测（240 步） | 1.32 ms | 预测便宜，可以大幅加厚 |
| 单次决策（约 17 候选 × 4 h） | 50 ms | 15 min 决策周期只占 0.006% CPU |
| 100 次扰动蒙特卡洛 | 5.0 s | 做鲁棒决策需要异步化，见 A3 |
| 30 天预热 | 101 ms | 启动态可以每次重建，无需快照 |
| 内存 | heap 14.8 MB | 多厂并发无压力 |

**结论：算力余量极大，质量的瓶颈不在性能，而在"模型可信"与"决策可信"。**

### 0.2 当前实现的可信度评分（我的自我审查）

| 维度 | 现状 | 评分 | 主要缺口 |
|---|---|---|---|
| 工艺模型 | 6 状态简化动力学 | 3/10 | 无 ASM 组分分离；参数手调无出处；无国际基准对照 |
| 水力/二沉池 | 单池固体通量 + 简化泥层 | 3/10 | 无 Takács 分层；无回流污泥浓度反馈闭环；无短流 |
| 数值方法 | 半隐式欧拉，1 min 步长 | 5/10 | 无步长自适应；无守恒性断言；无刚性处理 |
| 决策算法 | 枚举候选 + 加权目标 | 4/10 | 未声明优化问题；目标权重手调；无可行性保证 |
| 不确定性 | 无 | 1/10 | 单点预测，无置信区间，无鲁棒性 |
| 可解释性 | 模板化理由 | 4/10 | 理由与目标函数项无对应关系；无敏感性归因 |
| 可视化 | 工艺流程图 + 趋势 | 7/10 | 缺预测扇区、缺 Pareto、缺参数敏感性 |
| 工程化 | 31 测试、类型严格、审计 | 6/10 | 无持久化、无回放、无多用户 |
| 交互（对话） | 关键词意图 + 模板 | 3/10 | 非 LLM；无法处理复合问题 |

**总评：作为演示原型 7/10，作为可用于教学/方案对比的工具 4/10，作为可接管真实水厂的方向 1/10。**

## 1. 主线：把"物理"改成有出处、可验证的

这是唯一能让整个平台站住的一条线。其余所有质量提升都建立在它之上——如果模型不可信，AI 决策再花哨也只是精确的错误。

### A1. 迁移到 ASM1 组分体系（最高优先）

**现状问题**：现在引擎只有 6 个状态（COD、NH、NO₃、TP、SS、DO），是自己拼的简化模型。参数（kCod=1.4、kNit=14、kDen=4.6……）是为了让稳态落进合理区间手调出来的，没有任何文献出处。这在答辩或客户面前是硬伤。

**改成什么**：采用 IWA ASM1 标准组分（14 组分 / 8 过程），参数全部引自权威参数表。已核实的真实值：

```
组分（g COD/m³ 或 g N/m³）：
  S_I 30.00  S_S 69.50  X_I 51.20  X_S 202.32  X_B_H 28.17  X_B_A 0
  X_P 0      S_O 0      S_NO 0     S_NH 31.56  S_ND 6.95   X_ND 10.59
  S_ALK 7.00（mol HCO3/m³）        S_N2 0

化学计量：
  Y_H 0.67   f_P 0.08   Y_A 0.24   i_XB 0.086   i_XP 0.06

动力学（20 ℃）：
  mu_H 6.0    K_S 20.0    K_O_H 0.20   K_NO 0.5
  b_H 0.62    eta_h 0.4   eta_g 0.8
  mu_A 0.8    K_NH 1.0    K_O_A 0.4    b_A 0.15
  k_a 0.08    k_h 3.0     K_X 0.03
```

**厂区几何也一并换成 BSM1 权威值**（这样才有国际对照）：

```
反应池容积  (1000, 1000, 1333, 1333, 1333) m³  ← BSM1 五池
二沉池      面积 1500 m²，深 4.0 m，10 层，进料第 6 层
流量        平均 18 446 m³/d = 768.6 m³/h
内回流      55 338 m³/d
污泥回流    18 446 m³/d
剩余污泥    385 m³/d
开环曝气    KLa = (0, 0, 240, 240, 84) /d
饱和溶解氧  8.0 g/m³
```

**怎么证明改对了**：
- `tests/asm1.test.ts`：8 个过程的化学计量矩阵每列闭合（COD、N、电荷三本账逐项相加为给定值）
- 稳态出水与 BSM1 技术报告 Table 6 公开值逐项对照，误差在 ±10% 内（这是国际上公认的验证方法）
- 连续性检查：每个组分在每个单元的全厂物料平衡残差 < 0.1%

**代价**：引擎重写约 900–1200 行，3–5 天；现有 31 项测试大部分要按新状态重写。

**已实测的迁移障碍（`scripts/bsm1-gap.ts`）**：把当前引擎按 BSM1 几何对照后发现六项结构性不匹配，全部要求在迁移时一并处理，否则对照必然失败：

| 差异 | 当前实现 | BSM1 / ASM1 | 后果 |
|---|---|---|---|
| 池容 / HRT | 22 500 m³ / 11.25 h | 5 999 m³ / 7.81 h | 当前 HRT 是 BSM1 的 1.44 倍，硝化余量偏高，直接对照会"太好看" |
| 二沉池表面负荷 | 0.83 m³/(m²·h) | 0.51 m³/(m²·h) | 当前负荷是 BSM1 的 1.63 倍，泥位结论不可直接比较 |
| 生物量状态 | 单一 `biomassKg` | `X_B_H` + `X_B_A` 两个独立状态 | 无法表现"毒性只抑制硝化菌"这一真实机理，而这是当前主推场景之一 |
| 惰性 / 可降解组分 | 全部并入 `SS` | `X_I`(51.2) 与 `X_S`(202.3) 分开 | 产泥率与 SRT 无法与基准对照 |
| 碱度单位 | mg/L as CaCO₃ | mol HCO₃/m³ (7.0) | 需统一换算口径，否则 pH 与硝化缓冲判断错位 |
| 温度基准 | 运行时随季节变化 | ASM1 参数为 20 ℃；BSM1 报告用 15 ℃ 参数集 | 必须二选一并全程固定，否则对照失去意义 |

**这意味着 A1 不是"换参数"，而是"换状态空间"。** 3–5 天是按换状态空间估的，不要按改常数理解。

**进展（已完成）**：拓扑求解引擎已落地，见下一节。反应器数量由拓扑决定，不再固定五池。

**风险**：ASM1 不含磷。生物除磷需要接 ASM2d 或 Bio-P 模块。**建议分两步**：先完整迁移 ASM1（不含磷，用化学除磷兜底），下一步再叠 ASM2d 的磷模块。不要一次到位。

### A2. 二沉池换成 Takács 分层模型

**现状问题**：现在用"固体收支累积量 ÷ 浓度 ÷ 面积"推泥位，回流污泥浓度用一个经验公式反推。这导致回流浓度和池内浓度用的是两套不自洽的假设（开发中已经因此产生过一个真实缺陷：回流泵故障时泥位反而下降）。也无法表现污泥膨胀。

**改成什么**：BSM1 标准的 Takács 十层沉降模型。已核实的实测参数：

```
v0_max = 474 m/d      v0' = 250 m/d
r_h = 0.000576 m³/(g SS)   r_p = 0.00286 m³/(g SS)
f_ns = 0.00228          X_t = 3000 g/m³（阈值）
分层 10 层，每层 0.4 m，进料第 6 层，面积 1500 m²
```

每层用双指数沉降速度 v_s = max(0, min(v0'·(e^{-rh·X} − e^{-rp·X}), v0_max))，10 层串联做质量平衡，顶层溢流出水、底层抽回流污泥。

**怎么证明改对了**：
- 污泥界面高度随时间演化与 BSM1 报告 Figure 7 吻合
- 回流污泥浓度由底层浓度直接给出，不再需要经验关联式
- 回归测试：回流比从 0.3 扫到 1.5，回流浓度单调上升且落在 4000–12000 mg/L

**代价**：约 250 行 + 6 项测试，1–2 天。

### A3. 数值方法与守恒性

**现状问题**：半隐式欧拉，1 min 固定步长。没做过守恒性断言，也没测过步长收敛性。刚性工况（毒性冲击、停电恢复）下能否稳定，目前只有"跑完没 NaN"这一条弱证据。

**改成什么**：
- 加守恒性断言：每个时间步后检查全厂 COD/N/电荷总量，残差超阈值立刻抛错（fail-closed，不静默）
- 步长收敛测试：同一初值分别用 0.25 / 0.5 / 1 / 2 min 步长推进 24 h，结果差 < 1%
- 刚性场景用自适应子步：当某池 DO 或浓度变化率超阈值时自动细分

**怎么证明**：`tests/conservation.test.ts` 里三项全绿；并在 README 公布收敛阶。

**代价**：约 120 行 + 4 项测试，半天。

### A4. 参数标定与不确定性

**现状问题**：参数是手调的，没有回归过程，也没有不确定度。这就无法回答"你的结论有多可信"。

**改成什么**：
- 用 `scripts/calibrate.ts` 扩成真正的标定：先用 OAT 做敏感性排序，再对高敏感参数做网格/局部搜索
- 每个参数给出区间而非点值，跑 100–500 次蒙特卡洛，输出出水指标的 P10/P50/P90 与超标概率
- 前端展示"预测区间"而非单线

**怎么证明**：敏感性排序应稳定（同一 seed 重复跑 Spearman ρ > 0.9）；蒙特卡洛的超标概率随扰动幅度单调上升。

**代价**：约 300 行 + 可视化，2 天。**这是让"仿真"变成"可信仿真"的关键一步**，因为有了区间，AI 的每次决策才能说清"我有多少把握"。

## 2. 副线：把"决策"从枚举改成有目标的优化

### B1. 把决策显式写成优化问题

**现状问题**：现在是在 17 个手工候选里排序。这不是优化，是查表。目标函数权重（超标 2200、裕度 2600、成本 0.35……）是手调的魔数，且无法解释"为什么是这个权重"。

**改成什么**：写成标准形式

```
minimize    J = Σ_k [ w_q · max(0, C_k − C_k^lim)²  +  w_m · max(0, 0.85·C_k^lim − C_k)²  +  w_e · E + w_c · Chem ]
subject to  DO_min ≤ DO ≤ DO_max
            u_min ≤ u ≤ u_max
            Δu_max  （单步调节速率限制）
            SRT_min ≤ SRT(u) ≤ SRT_max
```

然后：
- 目标函数与惩罚项在 UI 里可调，并显示每个候选的**分项得分**（这样"为什么选它"就是可验证的，而不是一句模板话）
- 用 CMA-ES 或坐标下降做连续优化，不再依赖手工候选集

**怎么证明**：同一状态下，优化解的目标值 ≤ 枚举最优解；分项得分之和等于总分（自洽）。

**代价**：约 200 行，1 天。

### B2. 鲁棒决策（用上实测的 5 s 蒙特卡洛预算）

**现状问题**：现在只对单条预测负责。实际工况有进水波动、传感器噪声、参数不确定，最优解常在边界上，一阵扰动就失效。

**改成什么**：候选方案在 N 个扰动样本上评估，取**最坏情况的期望**或 CVaR。实测 100 次扰动重算 5 s，可以直接放在决策周期内（15 min 仿真时间绰绰有余）。

**怎么证明**：在同一场景下，鲁棒解在 50 次留出扰动下的超标次数 ≤ 名义最优解。

**代价**：约 150 行，1 天。这条对"可信"的边际收益非常高——它是从"我算了个最优"升级到"我知道这个最优有多稳"。

### B3. 决策可解释性升级

**现状问题**：`rationale` 是拼接的模板句子，`explainTweak` 是查表。它能读懂，但不构成"归因"。

**改成什么**：每句话都对应一个可核验的数字：
- "提高 DO 0.5 mg/L 使 4 h 内氨氮峰值从 4.8 降到 2.1"（来自实际预测差分）
- "代价是吨水电耗增加 0.021 kWh/m³，折合日成本 +¥380"
- "该结论对 k_NH 敏感：若 k_NH 低 15%，氨氮峰值升至 3.6"

最后一条需要 A4 的敏感性分析支撑。

**怎么证明**：每个数字都能从某次真实预测输出里复核；测试里断言"理由中的数字与预测结果一致"。

**代价**：约 200 行，1 天。

### B4. 对话层接 LLM（保留引擎做工具层）

**现状问题**：关键词匹配 + 模板。复合问题（"如果明天暴雨同时鼓风机坏一台，我该提前做什么"）完全答不了。

**改成什么**：引擎与决策层暴露为一组工具（`forecast(controls, scenario)`、`decide()`、`explain(candidate)`、`sensitivity(param)`），LLM 负责规划工具调用与组织语言。**严格约束**：所有数字必须来自工具返回，LLM 不得自行推算。

**怎么证明**：
- 建一组评测集（30–50 个问题，含预期数值范围），自动比对 LLM 回答是否引用了真实数据
- 幻觉检测：回答中出现的每个数字必须能在工具输出里找到

**代价**：约 400 行 + 评测集，2–3 天。**但没有 A1–A4 做底，接了 LLM 只会让"精确的错误"说得更流畅。**

## 3. 第三条线：把"看见"变成"看懂"

### C1. 预测可视化（当前最明显的缺失）

- 趋势图上叠加 4 h 预测扇形（P10/P50/P90），与历史用不同线型区分
- 决策面板画 Pareto 前沿（达标裕度 vs 成本），标出当前点、AI 建议点、人工基准点
- 工艺流程图把预测的 DO/氨氮以短时外推箭头显示

### C2. 敏感性可视化

- 参数—指标热力图（哪个参数对哪个出水指标影响最大）
- 决策敏感性：关键控制量在附近扰动时，预测超标的概率怎么变

### C3. 可解释的告警

现在告警只是"某指标超限"。应改成：触发条件 + 归因（哪个池、哪个控制量、哪段趋势）+ 建议动作 + 预测若不处理的后果。

### C4. 回放与对比

- 记录决策与状态快照，支持时间轴回放
- 支持"AI 值守 vs 人工固定策略"同场景双跑对比（现在是有基准数值但没有真正的双跑）

**代价**：C 线合计 3–4 天。

## 6. 我认为最容易被忽略、但决定成败的三件事

### 6.1 先定"验证基准"，再写代码

现在的验证是"数值看起来合理"——稳态出水 COD 17、氨氮 0.06，很漂亮，但没有任何外部依据说这些数字是对的。行业里判断仿真模型可信的标准只有一个：**基准案例对照**（BSM1 是公认的入门线）。没有这一步，所有"看起来专业"都是自证。

具体的：先写 `tests/bsm1-benchmark.test.ts` 的骨架（对照 Table 6 的具体数字），让它红着，再填实现。

### 6.2 不要一次做完 A1

ASM1 只有碳氮，没有磷。现在的模型有生物除磷 + 化学除磷，虽然简化，但至少覆盖了 TP 这个关键约束。**贸然全换会丢掉磷这个卖点**。正确顺序：ASM1（碳氮）+ 保留化学除磷 → 验证通过 → 叠 ASM2d 磷模块。每一阶段都保持可运行。

### 6.3 诚实标注"这是什么"

现在的 README 已经写了"仿真原型，不能替代 GPS-X/BioWin"。迁移到 ASM1 之后这条要**改**：ASM1 + BSM1 是可发表的模型，可以写"采用 IWA ASM1 标准模型并在 BSM1 基准上验证"。但也不能吹成"可用于工程设计"——那需要完整的 ASM2d、实测标定、以及独立第三方校核。

**可信度来自"边界说得准"，不是来自"功能看起来多"。**

## 10. 已完成：拓扑求解引擎

原计划把"引擎按拓扑生成反应器"列为第一位缺口。现已实现。

### 做了什么

| 文件 | 作用 |
|---|---|
| `src/sim/network.ts` | 拓扑 → 可求解网络：反应器编译、拓扑排序、流量求解 |
| `src/sim/networkEngine.ts` | 按拓扑动态生成 N 个反应器并求解的引擎 |
| `src/sim/plantModel.ts` | 厂模型抽象，AI 决策只依赖接口，不依赖具体引擎 |
| `tests/network.test.ts` | 21 项网络编译 / 流量 / 求解 / 预测一致性测试 |

### 关键设计

**1. 反应器来自拓扑，不来自代码**

```ts
for (const id of topo.train) {
  const unit = findUnit(topo, id);
  reactors.push({ id, kind, volume: unit.volume, ... });
}
```

引擎里没有任何"5 个池"的假设。加一个池子，就多解一个。

**2. 求解顺序来自连通性**

非回流边做拓扑排序，回流边在每步开头按控制量定流量。环路会被检测并拒绝。

**3. 流量按物料平衡传播**

每条边的流量 = 上游出流 - 被抽走的回流，多出口平分。空气与药剂边流量为 0（不计入水力）。
并联旁路（如调蓄池）不会被重复计入进水。

**4. AI 预测与被控对象用同一个模型**

这是最关键的一点。`PlantModel` 接口保证：

```ts
const model = networkModel(runtime.topology, runtime.net);
const rec = decide({ model });   // 预测用的就是拓扑引擎本身
```

避免了"改图改了 A 引擎，AI 却在用 B 引擎预测"的假闭环。

### 验证结果（`scripts/prove-network-solving.ts`）

| 拓扑 | 反应器 | 池容 | 出水 NH₄-N | 物理方向 |
|---|---|---|---|---|
| 标准 A²/O | 5 | 22.5k m³ | 0.11 mg/L | 基准 |
| 加一个缺氧池 | 6 | 27.0k m³ | 0.13 | TN 9.74→9.15（脱氮改善）|
| 加两个好氧池 | 7 | 32.5k m³ | 0.03 | 硝化更彻底 |
| 只留一个好氧池 | 3 | 12.5k m³ | 7.01 | **超标**，池容不足 |
| 删厌氧池（A/O）| 4 | 19.5k m³ | 0.09 | TP 失去生物除磷，靠化学兜底 |

浏览器实时验证（`scripts/e2e-topology-live.ts`）：

```

应用后：6 个反应器（+8000 m³），NH₄ 0.032
还原后：5 个反应器，NH₄ 0.110
```

### 与 A1（ASM1）的关系

这两件事是正交的，可以分别推进：

- **拓扑求解**（已完成）：解决"能搭任意结构"的问题 —— 结构自由度
- **ASM1 组分**（未做）：解决"模型有出处、可与国际基准对照"的问题 —— 模型可信度

现在的拓扑引擎用的仍是简化动力学（6 状态），但骨架已经对了：换成 ASM1 只需替换 `stepNetwork` 内部的速率表达式，反应器循环、流量求解、拓扑排序都不用动。

### 剩余限制（诚实记录）

1. **非反应器单元不建状态方程**：格栅、初沉池、消毒池只做流量传递，不计算去除率。初沉池的 SS 去除目前被忽略。
2. **回流取水点固定**：内回流永远从末端反应器取，污泥回流永远回第一个反应器。拓扑里的 `ir` 端口只用于接线校验，不影响取水位置。
3. **曝气按需分配**：每个好氧池独立按需氧量算 KLa，没有厂级风量约束（真实水厂总风量有限）。
4. **多出口平分**：分流器按均分处理，不支持任意比例分配。

## 12. 防漂移：常数单一来源 + 跨引擎一致性测试（已完成）

上一节第 5 条整顿时发现：两份引擎各自持有一份 `const K = {...}`。当时两份**完全一致**，
但没有任何机制保证以后仍然一致——改一处忘另一处，参考实现和生产实现就会悄悄分叉，
而所有"对照测试"都会随之失效（因为它对的是各自的副本，不是同一个真相）。

### 做了什么

**1. 抽出 `src/sim/kinetics.ts` 作为唯一来源**

```ts
export const KINETICS = { kNit: 14.0, yieldH: 0.48, ... } as const;
export const DESIGN_MLSS = 3400;
export const TARIFF = { electricity: 0.68, pac: 2.2, ... } as const;
```

`engine.ts` 与 `networkEngine.ts` 都从这里导入，`K.` 改为 `KINETICS.`。

**2. `tests/cross-engine.test.ts` 锁定三件事**

| 测试组 | 锁什么 |
|---|---|
| 常数单一来源 | 常数集中在 kinetics，且落在工艺常识区间（kNit 5–30、yieldH 0.3–0.7 等） |
| 行为方向一致 | 两引擎对"提高好氧容积 / 降低溶解氧 / 加大排泥"的响应方向必须相同 |
| 可复现性 | 同 seed 下各自确定性；进水设计值取自同一处 |

不要求两者数值相同——求解路径与初始条件本来就不同，强行对齐只会制造假精度。

**3. 反向验证测试真的能抓到漂移**

故意把 `kNit` 从 14.0 改成 1.4：

```
× 动力学常数集中在一处且不被两个引擎各自复制   expected 1.4 to be 14
× 关键常数落在工艺常识范围内                    expected 1.4 to be greater than 5
× 标准工况下两者出水都达标                      expected 24.1 to be less than 5
```

三项立即失败，其中出水氨氮从 0.1 飙到 24.1——说明测试不是摆设。常数已还原。

### 验证

- 类型检查 0 错误
- **100 项测试通过**（新增 8 项跨引擎一致性测试）
- 浏览器端到端 5 面板正常，控制台 0 错误
- 实时拓扑应用：5 → 6 → 5 反应器，NH₄ 0.099 → 0.032 → 0.101

### 仍然存在的限制

1. **两引擎的数值从未要求一致**：固定五池引擎有硬编码的池间流量分配，拓扑引擎按编译出的顺序与物料平衡求解，两者在相同输入下出水 COD 可差 10–20%。这是路径差异，不是错误。
2. **常数区间检查是"护栏"不是"验证"**：它只能挡住明显荒谬的改动（如数量级错误），挡不住"物理上说得通但标定错了"的参数。
3. **真正的可信度仍缺 BSM1 对照**：这一点在 `docs/QUALITY-ROADMAP.md` 第 1 节的 A1 里，尚未开始。

## 13. ASM1 组态实现（已完成，尚未接入主引擎）

这是路线图 A1 的第一步。**先做对模型，再换引擎**——顺序反了会拿错的东西去对标。

### 做了什么

| 文件 | 内容 |
|---|---|
| `src/sim/asm1.ts` | 13 组分 / 8 过程的化学计量与动力学，系数由参数推导 |
| `src/sim/asm1Cstr.ts` | 单池 CSTR 求解器，用于验证动力学能收敛到合理稳态 |
| `tests/asm1.test.ts` | 29 项：守恒律、量纲、世代时间、CSTR 稳态 |

### 关键设计：系数由参数推导，不硬编码

```ts
aerobic_growth_heterotrophs: {
  S_S: -1 / Y_H,
  S_O: -(1 - Y_H) / Y_H,
  S_NH: -i_XB,
  X_B_H: 1,
}
```

改 `Y_H` 时，基质消耗、氧耗、产率自动同步。写死的只有过程结构（谁消耗谁生成）。

### 守恒律验证（这是最有价值的部分）

不依赖任何外部文献就能严格检验。全部 8 个过程：

| 账目 | 结果 |
|---|---|
| 氮闭合 | 残差 ≤ 7e-18（机器精度） |
| 碱度闭合 | 残差 0 |
| COD 闭合 | 7 个过程 ≤ 4e-17；自养生长例外（见下） |

**自养生长的 COD 残差非零是正确结果**：硝化菌以 CO₂ 为碳源，生物量 COD 来自无机碳，不从有机 COD 池取。这个例外必须显式排除，否则会误判为错误。

### 过程中修掉的 5 个真实错误

这五个都不是笔误，是模型设计问题：

1. **缺氧生长的氮平衡漏了同化** —— 反硝化时生物量合成仍需氨氮
2. **量纲错误：ASM1 参数是 d⁻¹，我当成了 h⁻¹** —— 所有速率放大 24 倍
3. **自养生长归一化单位错** —— 以氮归一导致生长与衰减无法直接相减（`0.24×66.7 < 22.5`，硝化菌必然死亡）
4. **守恒检验的符号约定错** —— 硝酸盐作为电子受体，符号应与氧一致
5. **碱度判据错** —— 有机氮水解不涉及质子转移，不能用"一切氮转移"判断

第 3 个最隐蔽：它让硝化菌在任何条件下都活不下来，但表面上看只是"参数不合理"。

### 验证：硝化菌能否维持，取决于 SRT

这是 ASM1 实现真正跑起来的证据：

```
单池 HRT 5.2 h（无回流）
  → X_B_A = 0      硝化菌被冲出
  → S_NH  = 32.19  不达标

等效 SRT 10 d
  → X_B_A = 53.0   硝化菌维持
  → S_NH  = 0.74   达标
```

临界 HRT 判据：`1/(mu_A·S_O/(K_O_A+S_O) − b_A) ≈ 82 h`，与世代时间 25 h 同阶。

### 还没做的（重要）

- **未接入主引擎**：`networkEngine` 仍用 6 状态简化模型，ASM1 是并行验证的独立模块
- **没有 BSM1 Table 6 官方对照值**：搜索不可用、文献站点超时。我没有编造这些数字。已有的验证是守恒律 + 物理方向 + 量级合理性，这比"看起来对"强得多，但还不是官方基准对照
- **无磷**：ASM1 不含磷，迁移时需保留化学除磷或后续叠加 ASM2d

### 下一步的接口设计

接入时不需要改拓扑引擎的结构：

```ts
// 现在
stepNetwork(state, topo, dt)   // 内部用 6 状态

// 接入后
stepNetworkAsm1(state, topo, dt)  // 内部用 ASM1 13 状态，反应器循环不变
```

`network.ts` 的编译结果（反应器、顺序、流量）完全复用，只替换池内速率计算。

## 14. ASM1 接入试验：失败与诊断（已回退）

我尝试把 ASM1 接入拓扑引擎。**失败了，已回退。** 下面是完整诊断过程与结论，
因为这次失败本身比成功更有信息量。

### 试过什么

给 `ReactorState` 加可选 `asm1` 字段，加 `modelMode: 'simple' | 'asm1'` 开关，
在池循环里插入 ASM1 分支（13 组分求解后折算回聚合量）。拓扑编译与流量求解完全复用。

### 遇到的六个真实缺陷（都已定位并修复）

| # | 缺陷 | 表现 | 根因 |
|---|---|---|---|
| 1 | COD 映射不闭合 | 输入 COD 300 → 回算 2602 | 把 MLSS/1.42 当成生物量 COD，与总 COD 重复计算 |
| 2 | 进水含生物量 | 进水 `X_B_H = 106 mg/L` | `toAsm1` 在 `mlss=0` 时仍把 54% COD 分给生物量 |
| 3 | 生物量双轨 | 池内 `X_B_H` 与全局 `biomassKg` 各自演化 | ASM1 模式没从反应器汇总生物量 |
| 4 | 排泥基数错 | SRT 显示 2 d，MLSS 却在崩 | 排泥用二沉池回流浓度（10 000 mg/L），而池内只有数百 mg/L，差一个数量级 |
| 5 | 溶解氧塌陷 | 好氧池 DO 0.1 mg/L，硝化停滞 | 用简化 KLa 传质，ASM1 氧耗上百 g/m³/h 会在一步内抽干 |
| 6 | 流量求解叠加 | 池间流量 4200→7200→10200 | 两遍循环都用未确定的前向边流量累加（已修正为单遍传播） |

### 最终失败的原因（这是关键）

修完上面六项后，生物量仍然从 3331 mg/L 一路掉到 44 mg/L，而**出水 SS 只有 1.6 mg/L**。

即：生物量不是随出水流失的，而是凭空消失了。

进一步验证：**用 BSM1 自己的原始进水 + 自己的总池容做单池 CSTR，硝化菌同样归零**：

```
BSM1 进水（X_S 202 / X_B_H 28 = 7.2，S_NH 31.56）
总池容 5999 m³，HRT 7.8 h，单池等效
→ X_B_H 95, X_B_A 0, S_NH 32.29（硝化完全没发生）
```

**结论：任何活性污泥模型在"无污泥回流"的单池里都养不住生物量。**

ASM1 的生物量维持依赖二沉池截留 + 污泥回流构成的 SRT。当前拓扑引擎里：

- 二沉池仍用简化模型的关联式给出 `xRas` 与 `xEff`
- 这两个量与 ASM1 的池内生物量**没有任何耦合**

所以 ASM1 算出的生物量无法从二沉池"回收"回来。要把 ASM1 接进来，
**必须先把二沉池接到 ASM1 的颗粒态组分上**——也就是路线图 A2（Takács 十层沉降模型）。

### 这说明的顺序问题

我原以为顺序是：ASM1 → 二沉池 → 对照。
实际正确的顺序是：**二沉池（Takács）→ ASM1 → 对照**。

因为：
1. ASM1 的生物量守恒依赖二沉池的截留
2. 二沉池的固体通量依赖颗粒态浓度（ASM1 的 X_I/X_S/X_B_H/X_B_A/X_P）
3. 两者必须用同一套颗粒态定义，否则回流浓度对不上

### 保留了什么

- `src/sim/asm1.ts` —— ASM1 组态（13 组分/8 过程），守恒律精确闭合，29 项测试
- `src/sim/asm1Cstr.ts` —— 单池 CSTR 求解器，用于验证动力学
- `tests/asm1.test.ts` —— 全部通过

这些是有效的、可复用的资产。接入所需的二沉池模型尚未实现。

### 回退后的状态

- `networkEngine` 恢复为纯简化模型，129 项测试全过
- 拓扑求解、AI 决策、界面全部正常
- ASM1 以独立模块存在，不参与生产路径

### 教训

**接入一个更精细的模型，不是把它的状态塞进现有循环就行。**
它依赖一整套配套的边界条件（这里是二沉池与回流）。缺了配套，精细模型会比简化模型表现得更差——
因为它更"诚实"地反映了边界条件的缺失。

### 接入过程中修复的 5 个关键缺陷

1. **颗粒态被水力稀释** → 生物量几小时内归零。正解：颗粒态只随出水 SS 流失，不随 HRT 稀释
2. **流失比例用错分母**（`Q/qIn` 得 26%）→ 应算出水带走的固体份额（约 0.1%/步）
3. **进水含生物量**（`X_B_H=106`）→ 掩盖了真实的水力流失过程
4. **排泥基数用回流浓度**（10 000）而非池内浓度（数百）→ SRT 显示 2d 但 MLSS 在崩
5. **溶解氧被简化 KLa 抽干** → 改为设定值跟踪（供氧上限由 aerationCapacity 表达）

### 已知缺陷（未解决）

| # | 缺陷 | 影响 | 状态 |
|---|---|---|---|
| 1 | **浓缩区浓度梯度不足**：进料层以下 4 层浓度相同，回流浓度接近进料浓度而非 2–4 倍 | 回流污泥浓度偏低，SRT 偏高 | 未解决 |

| 3 | ASM1 的 TN 17.03 略超 15 | 出水总氮不达标 | 未解决 |
| 4 | 自养菌 X_B_A 达 6000（应 100–500） | 生物量结构偏离实际 | 未解决 |

缺陷 1 是根因：它导致回流浓度不足，进而使 SRT 与生物量结构都偏离。解决它需要重做浓缩区的数值格式
（当前用限制性通量，在层间浓度差小时会抹平梯度）。

### 默认值分叉（重要的工程事实）

Takács 的固体截留率显著高于原经验公式，同样排泥量下 MLSS 会持续上升。
因此**两个引擎使用不同的排泥基准**：

- `engine.ts`（参考实现）：`wasRatio = 0.0085`
- `networkEngine.ts`（生产路径）：`wasRatio = 0.022`

这是有依据的工程差异，不是遗漏。跨引擎测试已改为比较各自的相对变化，而非绝对值。

### 一个方法论上的教训
