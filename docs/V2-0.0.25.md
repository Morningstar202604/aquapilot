# AquaPilot V2 0.0.25 验收：服务运行时 MQTT 主题消费

> 基线：0.0.24 / `a467438`。本批把 MQTT 从“一次 CONNECT/CONNACK 检查”推进到服务运行时的真实订阅与遥测点位更新。仍没有现场 broker 凭据，因此验收对象是本地真实 MQTT 协议双端，不冒充现场设备验收。
> 质量门：`cargo fmt --all --check`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace` 全过（106 项）。

## 已做完

### 运行时订阅

- `AQUAPILOT_GATEWAY_CONFIG` 的 `mqtt` 段不仅用于 `gateway-check`，服务启动后会另起 MQTT 3.1.1 订阅循环。
- 订阅 topic 来自 `mqtt.topics`、`mqtt.topic` 或每个 `mqtt.read[].topic`；QoS 0，clean session，keepalive 30 s，空闲 15 s 发 `PINGREQ`。
- 收到 `PUBLISH` 后解析：裸数字、`{"value": n}`、或带 `point_id` 的 JSON；`value_path` / `path` 支持点路径；`scale` / `offset` 在映射里生效。
- 点位更新写回 `IndustrialHub`，`quality=good`；没有映射、非 JSON、非数字或未知点位不会改任何点位，只累计 `bad_payloads` 与 `last_error`。
- 断线后每 5 s 重连；`mqtt_runtime.state` 依次为 `starting / connecting / connected / error`，不会用上一次成功状态掩盖当前断线。

### 对外可见

- `GET /api/v1/industrial/adapters` 返回 `mqtt_runtime`：`connected`、`messages`、`bad_payloads`、`last_topic`、`last_point_id`、`last_value`、`last_message_at_unix`、`error`。
- `all_connected` 现在同时要求协议检查通过且 MQTT 运行时 `connected=true`；MQTT 断线时即使旧检查结果还是 true，也会 fail-closed 变 false。
- UI 工业网关显示 `mqtt · 3 · N msg`，并直接列出三条 MQTT 遥测：出水 COD / NH4-N / TP。
- 截图：`docs/screenshots/v2-ui-mqtt-runtime.png`（页面版本 `v0.0.25`，MQTT 3 个点位、持续增长的消息计数；截图当时 129 条消息，COD 40.000 mg/L）。

### 配置示例

```json
{
  "mqtt": {
    "broker": "127.0.0.1:18831",
    "client_id": "aquapilot-service",
    "timeout_seconds": 2,
    "read": [
      {"topic": "aquapilot/telemetry/effluent/cod", "point_id": "effluent.cod"},
      {"topic": "aquapilot/telemetry/effluent/nh4", "point_id": "effluent.nh4"},
      {"topic": "aquapilot/telemetry/effluent/tp", "point_id": "effluent.tp"}
    ]
  }
}
```

- 运行时 client_id 自动加 `-runtime` 后缀，避免与同一配置里的 `gateway-check` 探测连接互踢。
- 只连配置显式给出的 broker，不扫网、不订阅通配全部主题；`topics` 可使用 MQTT 通配符，但订阅集合由配置决定。

### 实机验收（本地协议双端）

- 本地 MQTT broker `127.0.0.1:18831` 接受 CONNECT/SUBSCRIBE，每 2 s 发布三条遥测。
- 服务 `127.0.0.1:5204`，配置 `/tmp/gateway-service-025.json`，DB `/tmp/aquapilot-gw25.sqlite`。
- 两次采样相隔 2 s：`effluent.cod` 40.0 → 41.5 mg/L，`effluent.nh4` 0.72、`effluent.tp` 0.148 保持；三条 `quality=good`。
- `all_connected=true`，`mqtt_runtime.state=connected`，`messages` 持续增长。
- 证据：`docs/cutover/gateway-runtime-mqtt-0.0.25.json`。
- 断线场景：停掉本地 broker 4 s 后 `mqtt_runtime.state=error`、`all_connected=false`（`last_check` 里旧的协议检查仍为 true，未掩盖断线）；重启 broker 后 8 s 内恢复 `connected=true`、`all_connected=true`。证据：`docs/cutover/gateway-runtime-mqtt-failclosed-0.0.25.json`。

## 未完成

- OPC UA 真实 SecureChannel/Session：仍未实现，`gateway-check` 明确 `unsupported`；没有拿 TCP 可达冒充会话。
- 现场验收：没有现场 PLC/网关地址、寄存器表、MQTT broker 地址或凭据；本批只证明本机真实 MQTT 协议双端。
- MQTT QoS 1 / 2、TLS、认证、保留消息、遗嘱消息未接入；当前只支持匿名 QoS 0 订阅。
- 24 h soak：`docs/soak-24h-summary.json` 不存在，`completed_24h=false`。
- Cutover 仍 **NO-GO**：BOD5 缺失、30 d COD/SS/TP 未过、24 h soak 未完成。

## 结论

0.0.25 关闭了“服务运行时只做 MQTT CONNECT 检查、点位不会由主题更新”的缺口：服务现在会真实订阅、解析并更新遥测点位，断线可见且 fail-closed。它没有关闭 OPC UA、现场设备验收、24 h soak 或 Cutover Gate。
