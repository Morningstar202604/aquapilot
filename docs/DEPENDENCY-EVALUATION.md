# 依赖评估：哪些换了成熟库，哪些刻意不换

> 原则：**能用成熟库就不自研，除非这是本项目的核心领域逻辑。**
> 但「换库」不是目的——一个已被 940 项测试覆盖、行为完全符合领域需求的模块，
> 换成通用库反而会丢掉领域语义。下面逐项记录判断依据，包括**不换的理由**。

## 一、已替换

| 模块 | 原实现 | 替换为 | 理由与收益 |
|---|---|---|---|
| WebSocket 消息校验 | `src/server/validation.ts` 手写 40 行 | `valibot` 1.5（`src/server/messageSchema.ts`） | 手写版只检查 `type` 是字符串，实测三处缺口：`scenario.kind` 任意值都按 start 处理、`sim.action` 非法值静默成功、`llmConfig.protocol` 未知值落入 Google 分支。schema 逐分支声明类型/枚举/长度/finite，非法输入在入口被拒。 |
| 客户端打包 | 单文件 bundle | Vite `manualChunks` + `React.lazy` | 首屏 JS 906 kB → 133 kB（gzip 294 → 41 kB）。 |
| 静态资源压缩 | 每请求 `gzipSync` | 按 (path, mtime) 缓存压缩结果 | 并发抓取时不再线性叠加主线程阻塞。 |

**为什么选 valibot 而不是 zod**：同为 schema 库，valibot 1.8 MB / zod 6.1 MB。本场景只做对象字段校验，valibot 的按 schema 树摇更省。两者能力都远超需求。

**安全细节**：valibot 默认错误文案形如 `Expected (...) but received "kill"`，会把客户端输入原样回射。本项目把错误收敛成固定措辞（只回字段路径 + 「类型或取值不在允许范围内」），避免反射注入串。

## 二、评估后不替换

| 模块 | 候选库 | 不换的理由 |
|---|---|---|
| 静态文件服务 | `sirv` (21 KB)、`serve-static` | 现有实现已有 14 项测试覆盖路径穿越、畸形编码、404 不回落、ETag、压缩协商、降级提示。换成通用库会丢失两条领域特定的行为：**「带扩展名的缺失资源必须 404，不能回落 index.html」**（否则浏览器把 HTML 当 JS 执行）和**「未构建时返回可读提示而不是 500」**。为省 160 行引入依赖不值得。 |
| HTTP 路由 | Express / Fastify / Hono | 当前只有 15 个只读 GET 端点 + 1 个 WebSocket 升级。引入框架会带来中间件链、body parser、错误处理语义的迁移成本，而现有路由有明确的 405/404/401 语义测试。**收益为负的替换不做。** |
| WebSocket 库 | `ws` | 已经是事实标准，本项目正在用。 |
| SQLite 访问 | `better-sqlite3` / Drizzle / Kysely | 使用 Node 22+ 内置 `node:sqlite`（零依赖、无需编译原生模块）。表结构只有 3 张、查询都是固定 SQL。ORM 会掩盖本项目最在意的两件事：**WAL 与 VACUUM INTO 的一致性**、**LIMIT 绑定值的类型约束**（已踩过 `datatype mismatch` 的坑）。 |
| 图算法（拓扑排序/环检测） | `graphology` / `dagre` | 本项目的图不是通用图：反应器子图排序要区分回流边与非回流边，环检测要给出可读的中文路径。通用库能算，但语义映射层的工作量 ≈ 自己写 40 行。 |
| 数值积分（ASM1/Takács） | `mathjs` / `ml-matrix` / `odex` | **这是本项目的核心领域逻辑，必须自研。** ASM1 化学计量守恒、Takács 界面通量格式的可复现性与质量守恒，都依赖对手写 RK/Euler 步进与子步数控制的完全掌控。通用 ODE 求解器无法表达「回流边不参与拓扑排序」这类领域约束。 |
| 决策算法 | `ml-matrix` / `simple-statistics` | 候选评分是领域加权（合规惩罚 2200/次、裕度惩罚 2600、成本 0.35），不是通用优化问题。引入求解器会丢失可解释性（每条 tweak 的理由来自领域规则）。 |
| 图表 | `echarts` | 已在使用，按需注册组件。 |
| 配置校验（Agent/LLM） | zod / valibot | Agent 配置的规范化包含领域规则（核心保护区、权限档位、控制量白名单），不是纯 schema 校验。schema 能校验形状，但校验不了「这个字段在 open 档位下才允许」。当前 `normalizeAgentConfig` 已覆盖并有测试。 |

## 三、明确不需要的依赖

| 能力 | 为什么不需要 |
|---|---|
| 日期库（dayjs/date-fns） | 全项目只用仿真分钟数与 `Date.toISOString()`，没有时区/日历运算。 |
| 状态管理（Redux/Zustand） | 单一 WebSocket 数据源 + 本地 UI 状态，React 内置状态足够。引入会掩盖快照合并的真实逻辑。 |
| 表单库（react-hook-form） | 只有两个设置面板，字段校验在服务端。 |
| CSS 框架（Tailwind） | 已有 55 KB 手写 CSS 与设计 token（`--line`、`--text-1` 等），换框架等于重做视觉。 |
| 日志库（pino/winston） | 自研 `observability.ts` 已实现 JSON Lines + 脱敏 + 永不抛出，且与指标同源。pino 会引入 worker 线程与额外配置。 |

## 四、判断标准（供后续复用）

一个问题决定是否换库：

1. **这是领域核心吗？**（ASM1、Takács、拓扑求解、决策评分）→ 自研。
2. **现有实现有测试覆盖且行为正确吗？** → 不换，除非新库能消除一整类缺陷。
3. **新库能带来可测量的收益吗？**（体积、正确性、安全边界）→ 能量化才换。
4. **换库会丢失领域特定行为吗？**（如静态服务的 404 不回落）→ 不换。

按这四条，本轮只换了 1 个模块（WS 校验），因为它是唯一同时满足「有真实缺口 + 通用库能完整覆盖 + 不丢领域语义」的。
