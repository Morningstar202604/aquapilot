# 界面与可视化编排架构

> 回答一个问题：一个"各种工艺、各种部件、各种连线"的仿真平台，界面该长什么样，
> 而且这些图必须**真的能跑**，不是画出来的。

---

## 一、核心判断：图不是画面，图是模型

主流工艺仿真软件（Aspen HYSYS、GPS-X、BioWin、SIMBA#）以及工业 DCS/SCADA
（WinCC、iFIX、Ignition）有一个共同点，也是最容易被做前端的人忽略的一点：

**流程图上每一个方块、每一条线，都是求解器里的一个对象，不是一份绘图数据。**

反过来做（先画图，再想办法让数字动起来）必然导致三个后果：

1. 图能画，但跑不了——新增一个池子，引擎不认识它
2. 数字对不上——图上标 5000 m³，引擎里还是硬编码的 5000
3. 改图无意义——用户拖了半天，结果仿真结果一点不变

所以这个项目的第一条设计原则是：

> **拓扑（topology）是唯一真相源。界面、引擎、告警、校验都从它派生。**

### 三层结构

```
   ┌─────────────────────────────────────────────┐
   │  拓扑层  src/model/topology.ts               │
   │  单元（UnitSpec）+ 物流（Connection）        │
   │  没有坐标、没有颜色、没有像素                │
   └──────────────┬──────────────────────────────┘
                  │
     ┌────────────┼────────────┐
     ▼            ▼            ▼
  布局层       求解层        校验层
  layout.ts   topologyEngine  validate + readiness
  坐标/路径   池容/流量/HRT  阻断/警告
     │            │            │
     └────────────┼────────────┘
                  ▼
   ┌─────────────────────────────────────────────┐
   │  渲染层  PlantCanvas / ProcessEditor         │
   │  只负责把"已算好的状态"画出来                │
   └─────────────────────────────────────────────┘
```

关键约束：**渲染层不持有任何工艺知识**。它不知道什么是厌氧池，只知道"有个单元，
它的状态是这些数字，它的端口连到那里"。

## 二、节点怎么设计

### 2.1 单元类型（UnitKind）

按工艺功能分类，不是按外形：

| 类别 | 类型 | 典型部件 |
|---|---|---|
| 预处理 | `screening` `grit` `primary` | 格栅、沉砂池、初沉池 |
| 生物处理 | `anaerobic` `anoxic` `aerobic` | 厌氧/缺氧/好氧池 |
| 固液分离 | `clarifier` `disinfection` | 二沉池、消毒池 |
| 调蓄 | `storage` | 雨水调蓄池 |
| 公用工程 | `blower` `chemical` `pump` | 鼓风机房、加药间、泵 |
| 污泥线 | `thickener` `dewatering` | 浓缩池、脱水机房 |
| 边界 | `inlet` `outlet` | 进水渠、排放口 |

### 2.2 单元携带的信息

```ts
interface UnitSpec {
  id: string;            // 求解器用它做键
  kind: UnitKind;        // 决定用什么方程
  name: string;          // 显示名
  role: string;          // 工艺角色（"硝化 · 有机物氧化"）
  volume?: number;       // 池容 m³ —— 引擎真的会用
  area?: number;         // 面积 m² —— 二沉池用
  depth?: number;        // 池深 m
  ports: Port[];         // 端口：连接唯一允许的挂载点
  states?: string[];     // 参与的 state 变量
  interventions?: InterventionKey[];  // 允许人工干预什么
  meta?: Record<string, ...>;         // 设备参数（栅距、曝气器数量…）
}
```

`interventions` 这一项很关键：**控制面板上的控件是拓扑生成的，不是硬编码的**。
把鼓风机删掉，DO 设定滑块就自动消失，因为没人声明它可调了。

### 2.3 端口与物流

端口是连线的唯一合法挂载点。不允许"从方块边框任意位置拉一条线"——那样无法校验。

物流分九种，每种有自己的视觉编码：

| 物流 | 颜色 | 线型 | 含义 |
|---|---|---|---|
| `influent` | 青绿 | 实线 | 进水 |
| `mixed_liquor` | 暗青 | 实线 | 池间混合液 |
| `internal_recycle` | 亮青 | 点线 | 内回流（硝化液回流） |
| `return_activated_sludge` | 琥珀 | 虚线 | 污泥回流 |
| `waste_sludge` | 褐 | 点划 | 剩余污泥 |
| `effluent` | 青绿 | 实线 | 出水 |
| `air` | 淡蓝 | 细点 | 曝气 |
| `chemical` | 紫 | 细点划 | 药剂 |
| `sludge_cake` | 棕 | 粗点划 | 泥饼 |

**颜色只编码物流类型，不编码状态**。状态（超标/正常）用描边和角标表达。
这是 DCS 的通行做法——如果颜色既表示介质又表示报警，操作员会误读。

## 三、布局：读图路径决定一切

### 3.1 主流软件怎么排

看过 GPS-X、BioWin、Aspen 的工艺图会发现共同的读图规则：

1. **主物料流永远水平、从左到右、不被打断**
2. **公用工程（鼓风、加药）挂在主要服务对象正下方**
3. **污泥线作为独立的第三条水平带，挂在二沉池下方**
4. **回流线绕外侧走，绝不穿过池体**

### 3.2 本项目的实现

`src/model/layout.ts` 按这三条规则自动排版，不手写坐标：

```ts
GAP_X = 46   // 主线水平间距
GAP_Y = 74   // 泳道垂直间距
```

- **主线顺序**：从进水口沿非回流边做深度优先遍历，得到真实读图顺序
  （进水→格栅→沉砂→初沉→厌氧→缺氧→好氧 A/B/C→二沉→消毒→排放）
- **公用工程**：锚定到它第一个下游目标的正下方，避免斜跨主线
- **污泥线**：对齐到二沉池正下方，让"泥从哪来"一眼可见
- **回流**：内回流走主线上方，污泥回流走主线与公用工程之间的走廊

> 踩过的坑：最初把二沉池归到 `recycle` 层（因为它连着回流线），
> 结果它根本没有坐标，四条连接线全部为空。教训是：
> **"参与回流"不等于"是支线"，二沉池是主线上的主工艺单元。**

### 3.3 泳道标注

画布上有三条虚线泳道，左侧标 `主处理线 / 公用工程 / 污泥线`。这不是装饰——
它是告诉第一次看这张图的人"从哪读到哪"。

## 四、视觉编码：什么该动，什么不该动

### 4.1 动态元素（表达物理状态）

| 元素 | 编码方式 | 数据来源 |
|---|---|---|
| 物流方向与流速 | 沿路径流动的高光点，速度随流量 | `Q` |
| 好氧池池体亮度 | 填充透明度随 DO 升高 | 池内 DO |
| 二沉池泥层 | 底部梯形色块高度 | 泥位 / 池深 |
| 泥位警戒线 | 琥珀虚线，超限变红 | 泥位 vs 池深-0.4 |
| 曝气气泡 | 池内上浮圆点，密度随 DO | DO |
| 单元告警 | 描边变红 + 右上角红点 | activeAlarms 关联 |
| 调蓄池存量 | 底部进度条 | 存量 / 容量 |

### 4.2 静止元素（表达结构）

池体边框、管道走向、泳道、图例、单元名——这些**永远不动**。
一旦它们开始闪、开始变色、开始动画，操作员就失去了参照系。

这条规则在监控界面里比"炫不炫"重要一百倍。

### 4.3 不用红色表示"正常但数值低"

工程界红黄绿的含义是固定的：红=故障、黄=偏离、绿=正常。
本项目的做法是：**只有告警才用红色**，正常态用青绿或中性灰。
DO 低但没触发告警时，只是池体亮度低，不染红。

## 五、可视化编排：怎么保证"画了就能跑"

这是最容易做成玩具的部分。这里是完整的三道闸门。

### 5.1 第一道：结构校验（`validateTopology`）

```ts
BAD_PORT      连接引用了不存在的端口
MISSING_UNIT  连接引用了不存在的单元
SELF_LOOP     自连
DUP_UNIT      ID 重复
DEAD_END      进水无出口 / 排放无入口
NO_INPUT      单元没有入口物流（警告）
NO_OUTPUT     单元没有出口物流（警告）
```

### 5.2 第二道：可运行性校验（`checkRunReadiness`）

结构对了不等于能跑。这一层检查工艺完整性：

| 阻断条件 | 为什么阻断 |
|---|---|
| 主序列为空 | 没有任何单元参与生物反应 |
| 没有二沉池 | 泥水分离失去物理依据，出水 SS 是编的 |
| 没有好氧池 | 无法完成硝化，出水氨氮必定超标 |
| 好氧池无容积 | 无法计算氧传递 |
| **新增单元未接线** | 图上画了却不在物流里 —— 最危险的假象 |
| 缺进水/排放单元 | 边界不完整 |

| 警告条件 | 为什么不阻断 |
|---|---|
| HRT < 6 h | 可能硝化不完全，但极小厂也能跑 |
| HRT > 24 h | 池容投资过剩，不影响求解 |
| 无污泥回流 | 生物量会流失，但短时可运行 |
| 无内回流 | 脱氮能力受限，不影响碳氧化 |

> 踩过的坑：最初"未接线"只给警告。实测发现用户加了一个好氧池，
> 校验显示"通过"，应用后发现出水完全没变——因为那个池子根本没进物流。
> **画了但没接线的单元必须阻断，不能只警告。**

### 5.3 第三道：应用时重建（`applyTopology`）

点"应用到仿真"时，服务端：

1. 重跑 `validateTopology` + `checkRunReadiness`
2. 不通过 → 拒绝，原运行时**不改动**（版本号不变）
3. 通过 → 用新拓扑的几何重建引擎，重跑 30 天预热，版本号 +1
4. 广播给所有客户端，AI 重新生成决策

### 5.4 闭环证明

有测试专门证明"改图真的改变结果"（`tests/topology.test.ts`）：

```
好氧池容积 ×2   → 出水 NH₄-N  0.074 → 0.034 mg/L   （更小，正确）
好氧池容积 ÷2   → 出水 NH₄-N  0.074 → 1.149 mg/L   （更大，正确）
二沉池面积 ×2   → 泥位 1.15 → 0.66 m                （更薄，正确）
回流泵故障      → 泥位 0.99 → 1.79 m                （抬升，正确）
```

这四条断言比任何截图都更有说服力。

## 六、两个视图，两种用途

### 6.1 运行监视（`PlantCanvas`，`fit="fill"`）

- 占用主区，按原始比例绘制，容器横向滚动（`min-width: 1680px`）
- 泳道间距 150px，比编排视图更疏，便于扫读
- 配 KPI 条、趋势图、AI 对话
- 点击单元 → 右侧显示该单元详情

> 这里踩了三次坑，记录结论：**宽扁的工艺图塞进 4:3 容器，任何"缩放适配"都会牺牲可读性**。
> 试过 `meet`（缩小后文字读不清）、垂直居中（留白无法利用）、自动折行（回流线穿越严重）。
> 最终选横向滚动 + 保持原始比例 —— 这也是 WinCC、Ignition 处理宽流程总览图的标准做法。

### 6.2 工艺编排（`ProcessEditor`，`fit="flow"`）

三栏布局，和主流流程模拟器一致：

```
┌─────────┬────────────────────────────┬──────────┐
│ 组件库  │  画布（按图纸尺寸 + 缩放）   │ 属性面板  │
│ 按工艺  │  顶部：状态 / 校验计数 /    │ 属性｜物流│
│ 分组    │  缩放 / 恢复标准厂 / 应用   │ ｜校验    │
└─────────┴────────────────────────────┴──────────┘
```

- 画布按真实尺寸绘制，外层滚动（大厂也能完整编辑）
- 缩放 50%–200%，1:1 复位
- 组件库 13 种部件，点一下即加入画布
- 连线：属性面板点出口端口 → 画布点目标入口端口
- **未应用时顶部有琥珀色横幅警告**："运行中的厂仍是旧拓扑"

## 七、和主流产品的对照

| 能力 | Aspen HYSYS | GPS-X | WinCC | 本项目 |
|---|---|---|---|---|
| 单元库拖拽编排 | ✓ | ✓ | ✓（图元） | ✓（13 种） |
| 连线合法性校验 | ✓ | ✓ | 部分 | ✓（端口级） |
| 可运行性检查 | ✓（收敛性） | ✓ | — | ✓（工艺完整性） |
| 拓扑直接驱动求解 | ✓ | ✓ | — | ✓（几何映射） |
| 回流可视化 | ✓ | ✓ | — | ✓（外侧绕行） |
| 泳道分区 | 部分 | — | — | ✓ |
| AI 决策叠加在图上 | — | — | — | ✓ |
| 实时 WebSocket 推送 | — | — | ✓ | ✓ |

> **必须说清楚**：本项目的"拓扑驱动求解"目前是**几何映射**——
> 拓扑里的池容、二沉池面积会真实覆盖引擎参数，但引擎内部仍固定是
> 五池串联结构。要做到 Aspen 那种"任意搭多少个池子都能解"，
> 需要引擎按 `topo.train` 动态生成 CSTR 并做拓扑排序求解，
> 这是 `docs/QUALITY-ROADMAP.md` 里 A1 的一部分，还没做。
>
> 这不是小事：现在的限制是**你能改参数，但不能改结构**。
> 加一个池子只会被拒绝（因为未接线），不会真的多一个反应器。

## 八、如果要继续做，优先级

1. **引擎真正按拓扑生成 CSTR**（当前最大缺口）
   - 现在：拓扑 → 几何映射到固定五池
   - 目标：拓扑 → 动态生成 N 个 CSTR → 拓扑排序 → 求解
   - 代价：约 400 行 + 重写池循环

2. **连线交互的图形化**
   - 现在：点端口 → 点端口（可靠但不直观）
   - 目标：拖拽连线 + 吸附端口 + 非法连接实时反馈
   - 建议用 React Flow（1.2 MB 解包，依赖 zustand），或自写 200 行
   - 自写的理由：现在的 SVG 坐标系统已经完整，加拖拽不需要引入整个库

3. **单元级下钻**
   - 点二沉池 → 十层浓度剖面
   - 点好氧池 → 沿程 DO/氨氮曲线
   - 数据已经都在 `SimState` 里，只差视图

4. **拓扑版本与回放**
   - 每次 apply 存一版，支持"回到第 2 版"
   - 需要先做 SQLite 持久化

5. **P&ID 模式**
   - 同一份拓扑，切换成带仪表位号（FT-101、DO-201）的工程图
   - 拓扑里已有 `meta` 字段可以挂位号

## 九、一句话总结

界面设计在这类平台上不是美术问题，是**数据模型问题**。

图上的每个方块、每条线都必须是求解器里的对象，否则做出来的就是一个会动的 PPT。
本项目的做法是：拓扑 → 布局 → 渲染三层严格分离，加两道校验闸门
（结构 + 可运行性），再用测试证明"改图真的改变结果"。

剩下的缺口是引擎还不能真正按拓扑生成反应器——这件事排在路线图第一位。
